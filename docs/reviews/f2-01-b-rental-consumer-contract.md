## 1. Smallest business outcome: draft rental contract (PROPOSED)

- Endpoint: `POST /workspaces/{id}/rental/contracts` (route example VERIFIED, `docs/06-ux-api.md:38`; no such route exists in runtime — `services/business-api/main.go:132-138` lists 19 routes, zero rental). Read: `GET /workspaces/{id}/rental/contracts` (list only; no GET-single in this slice — list demonstrates, and the handler reads rows directly in its own transaction, same reasoning as F2-01 §2).
- Request body (strict JSON, 16 KiB bound, same facilities as F2-01-A): `{"customer_id":"<uuid>","catalog_item_id":"<uuid>","starts_at":"<RFC3339>","ends_at":"<RFC3339>"}` plus a required `Idempotency-Key` header (see §4). Response 201: `{"id","workspace_id","customer_id","catalog_item_id","client_request_id","status":"draft","starts_at","ends_at","created_at","updated_at"}` (UTC, same conventions as F2-01-A). List: `{"items":[...]}` ordered `(created_at, id)`, pagination limit 1–100 default 50, offset ≥ 0.
- State: `status` is `draft` only (CHECK `status='draft'`); no transitions in this slice. A draft IS a recorded intent to rent — customer + item + period, created while Rental is entitled+active by an authorized user. It is NOT a reservation, an availability proof, a price, a handover, or a completed/active rental. Never call it an operational/completed rental.
- Why draft first (decision D-SLICE-1, §8): the guard is the point of F2-01-B. Pricing is a separate subsystem — bitemporal `price_versions` + currency + snapshot validation (`docs/02-core-data.md:22-24`) — that would double the slice and delay guard proof. A priced contract without a proven guard is higher-risk. The draft proves guard + reference + transaction + audit + concurrency with real data and no invented prices.
- Demonstration: owner creates a customer + item via the API, activates `rental.basic` (synthetic entitlement, isolated QA), creates a draft 201, lists it 200, shows the guard matrix, concurrent same-key creates yield one row, and deactivation/revocation makes future creates 403 while drafts remain readable history.

## 2. References, permissions, RLS (PROPOSED)

- Reference checks run in the SAME tenant transaction as the guard + insert (after the workspace-row lock): `SELECT id FROM parties WHERE workspace_id=$1 AND id=$2 AND type='customer'` (the type check is defense-in-depth; 005 locks `type='customer'`, `services/business-api/migrations/005_core_master_data.sql:31`); `SELECT id FROM catalog_items WHERE workspace_id=$1 AND id=$2 AND status='active'` (005:43).
- Missing OR cross-tenant id → the identical 404 (`"pelanggan tidak ditemukan"` / `"barang tidak ditemukan"`): no existence disclosure, no cross-tenant link. An archived item exists here but is not rentable → 409 (`"barang tidak aktif"`). A non-customer type (only possible if a future migration widens the type) → 404: the id denotes no customer in this workspace.
- FK design: composite tenant FKs — `FOREIGN KEY (workspace_id, customer_id) REFERENCES parties(workspace_id, id)` and `FOREIGN KEY (workspace_id, catalog_item_id) REFERENCES catalog_items(workspace_id, id)`. Pattern is spec-grounded: `docs/02-core-data.md:38` ("foreign key yang menyertakan konteks tenant"); `sql/001_core_reference.sql:48` shows the composite FK for `price_versions`. It needs `UNIQUE(workspace_id, id)` on both tables — added by migration 006 as `CREATE UNIQUE INDEX IF NOT EXISTS` (inherently satisfiable: `id` is the PK). The FK is the backstop, not the error path: the handler checks first (an FK violation would surface as 500, never as a client error).
- Permission matrix: create uses `manage_business_data` (owner+manager, seeded by 005); list uses `view_workspace` (owner/manager/cashier). Cashier create → 403; non-member/unknown workspace → 403; unauthenticated → 401. User permission is separate from module entitlement/installation: a manager with `manage_business_data` but no rental entitlement still gets 403 from the guard, and an entitled caller without the action permission gets 403 from the permission check. Before the reference reads, the guard explicitly checks `view_workspace` (the `e70cd9d` Finding-1 lesson: a silent RLS-filtered read is not authorization): denied → 403, query error → 500.
- RLS/grants on `rental_contracts`: bootstrap-owned, ENABLE+FORCE; SELECT policy (tenant + `app.is_member` + `view_workspace`); INSERT policy (tenant + `manage_business_data`); no UPDATE/DELETE policies; runtime grants SELECT, INSERT only. Mirrors 005. Audit in the same transaction: action `rental_contract_created`, `entity_type` `rental_contract`, `entity_id` the new contract UUID, details minimal identifiers only (no names); audit failure → rollback 500. History retention: deactivation/revocation never deletes drafts (`docs/02-core-data.md:52`; repo `AGENTS.md:13`).

## 3. Guard, wired with the endpoint (PROPOSED)

- Location: inside `handleCreateRentalContract` (new `rental.go`), NOT a standalone helper. No guard code exists before this endpoint (F2-01 §4 deferred it here). Reuse existing machinery: `hasPermission` (`services/business-api/workspace.go:100`), `lockWorkspace` (`services/business-api/modules.go:156`), `loadInstallation` (`modules.go:183`), `hasEntitlement` (`modules.go:227`), `loadActiveModules` (`modules.go:200`).
- Order inside the transaction (after `requireDB`, `authedSubject`, `isValidUUID`, strict body decode + period validation → 400): (1) `beginTenant` + `hasPermission` `manage_business_data` → query error 500 (`"izin gagal diperiksa"`), denied 403. (2) `lockWorkspace` (`SELECT id FROM workspaces WHERE id=$1 FOR UPDATE`) → no visible row 403. (3) Load the installation: none/inactive → 403 (`"rental belum aktif di workspace ini"`); take its exact version, then `hasEntitlement(tx, ws, "rental.basic", version)` → false → 403 (`"rental belum menjadi hak workspace ini"`). (4) Explicit `view_workspace` check → 403/500 (§2). (5) Reference reads (§2) → 404/409. (6) Idempotency-key lookup (§4) → existing draft → 200 replay. (7) INSERT + audit → commit → 201.
- Revocation: entitlement is re-checked at request time. Revoked rights deny future creates even if the B3 installation row still says active (the B3 no-op returns an existing intent snapshot, `modules.go:410`); the guard NEVER treats installation-active alone as sufficient.
- Backend failures: any guard query error (permission, entitlement, installation, reference read, lock) → controlled 500, never allow, never masquerade as 403. The handler distinguishes `err` (500) from `allowed=false` (403) — the existing `hasPermission` convention.
- Errors: flat envelope `{"error": msg}` (existing `writeError`), Indonesian messages, no SQL details. `docs/06-ux-api.md:44-50` shows a typed envelope with code `MODULE_NOT_ACTIVE` — that is an illustrative spec example, NOT adopted here: this task requires flat errors and no invented code envelope. The inactive case returns flat 403 `"rental belum aktif di workspace ini"`. A typed-envelope migration is a separate, later decision — not smuggled into this slice.

## 4. Transaction and concurrency (PROPOSED)

- One transaction: authorization → lock → guard checks → reference checks → key lookup → INSERT + audit → commit. Rollback on any failure; no partial draft or audit. `Idempotency-Key` is required (non-blank, max 128 chars, stored as `client_request_id`); missing key → 400. `docs/06-ux-api.md:42` requires `Idempotency-Key` for mutations where applicable.
- Lock: the SAME B3 workspace-row lock (`modules.go:156`), acquired after authorization and before any guard read, held until commit/rollback. B3 activation/deactivation take the same lock, and entitlement grant/revoke fixtures take the same lock (B3 ticket; `grantEntitlement` helper). READ COMMITTED (effective isolation verified by B3) suffices because the lock serializes the writers that could change the guarded state.
- Interleavings: create vs deactivate → serialized: deactivate-first → create sees inactive → 403; create-first → deactivate proceeds and the draft stands as history. Create vs revoke → the same: revoke-first → 403; create-first → the draft stands, future creates 403. Create vs create (same key) → serialized by the lock + pre-INSERT key lookup + `UNIQUE(workspace_id, client_request_id)` backstop → one 201 + one 200 replay of the same draft, exactly one row + one audit. Create vs create (different keys, same item+period) → both 201: no overlap protection — a stated limit (§5), not a bug. A repeated key with a different body returns the first draft (documented misuse: the key identifies the request).
- Reference rows cannot disappear mid-transaction via the API (no DELETE endpoints for `parties`/`catalog_items`, F2-01-A); the composite FKs are the backstop.
- Tests must be handler-level (real HTTP + real PostgreSQL): races via parallel requests (B3's `parallel` helper pattern), rollback via audit/insert fault triggers (F2-01-A pattern). A lock probe or a direct helper test is NOT endpoint enforcement evidence. No invented operator authority: tests use bootstrap fixture grant/revoke under the same lock (B3 pattern).

## 5. Money and pricing: deliberately absent (PROPOSED)

- This slice records NO money: no amount, no currency, no `price_version`, no `pricing_rule_version_id` columns. A draft cannot authorize handover, payment, price binding, or stock reservation.
- A `catalog_items` row is NOT a rentable physical unit: the rentable unit is `physical_asset` — "unit fisik serializable yang mengacu item" (`docs/02-core-data.md:15`) — which does not exist in runtime (grep: zero matches in `migrations/` and `*.go`). One item row proves no stock availability; availability/overlap needs a reservation with hold TTL + state (`docs/02-core-data.md:18`) and a stock ledger (`docs/02-core-data.md:27`) — later slices. The P3 gate "2 employees editing same asset cannot double-book" (`docs/08-roadmap-tests.md:31`) is NOT satisfied by this slice — stated, not claimed.
- When pricing comes (later slice), the shape is spec-grounded: `price_versions (workspace_id, item_id, price_list_id, valid_from, valid_to, amount_minor, currency, recorded_at)`, interval `[from,to)` non-overlapping (`docs/02-core-data.md:22`; reference sketch `sql/001_core_reference.sql:37-49` with `amount_minor BIGINT CHECK >= 0`, `currency char(3) DEFAULT 'IDR'`, composite FK). A contract stores `pricing_rule_version_id` AND the agreed unit amount (`docs/02-core-data.md:24`); master price fixes never silently change posted contracts; amounts are integer minor units, never binary floats; posted money is immutable and corrected only through controlled adjustments (repo `AGENTS.md:13`). No legal/tax compliance is claimed.
- Manifest note: `rental.basic` declares `needs_approval_for_mutations: false` (`examples/rental-basic.module.json:42`) — no financial approval framework is required for this no-money slice; a priced slice re-examines this.

## 7. Acceptance (PROPOSED)

- Happy path: owner creates a customer + item (201s), activates `rental.basic` with a synthetic entitlement (200), creates a draft 201 (exact fields, status `draft`, UTC timestamps), lists 200 (draft present, only own-workspace rows). Audit row correct: action `rental_contract_created`, `entity_id` the draft UUID, details minimal identifiers.
- Disabled Rental: no installation → create 403; inactive installation → create 403. Entitlement: absent → 403; revoked after activation → future create 403 (installation still active intent); re-activation after revoke → 403 (B3 behavior preserved).
- Roles/tenant: cashier create 403; manager create 201; non-member create/list 403; cross-tenant list shows only the requested workspace; unauthenticated 401.
- References: unknown customer/item → 404; cross-tenant customer/item → 404 with the identical message; archived item → 409; `ends_at <= starts_at`, missing dates, or missing key → 400.
- Backend 500: fault each guard query (permission, entitlement, installation, reference read, lock) → 500, no draft, no audit; restore in `finally`; create succeeds after.
- Rollback: audit-insert fault → 500, no draft; contract-insert fault → 500, no audit.
- Duplicates/concurrency: same key twice → one 201 + one 200 same draft, exactly one row + one audit; concurrent same-key → the same outcome; different keys, same item+period → two 201s (no overlap protection — limit, not a bug); create vs deactivate race → serialized (403, or 201-then-history, never a half-written draft and never a draft created after deactivation commits).
- Retention: after deactivation + revocation, drafts remain listable (200) and audit history intact; no DELETE anywhere.
- Limits: a draft authorizes nothing operational (§5); list pagination as F2-01-A; body 16 KiB. A provider probe or direct helper test is not endpoint enforcement evidence — all of the above go through the real handler.
