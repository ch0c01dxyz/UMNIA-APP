## 3. When a capability truthfully satisfies Rental (PROPOSED)

- Readiness is not a declaration. B3 activation records entitled intent; it does not prove a provider exists, is readable, or holds the referenced row. A capability satisfies `rental.basic`'s dependency only when all three hold: (1) the core tables exist and the readiness marker is present; (2) the tenant-scoped probe read succeeds at activation time (§2); (3) at consumption time, the specific referenced customer/item row exists and is readable in this workspace — a real SELECT inside the contract transaction (§4). Failing (3) is a client error about the reference, not a provider outage.
- What does NOT count as readiness: a manifest `provides` entry, an activation returning 200, a catalog list response, a synthetic probe, a helper test, or an availability ping. The probe and the per-reference SELECT are the readiness evidence because they are the actual reads the business path performs.
- Minimal responsible-layer integration: the resolver probe (§2, activation time) plus the per-reference SELECT (§4, consumption time). No invented health platform, no broad registry rewrite, no `healthy` column, no background checker. If the probe query errors, activation fails 500; if the reference SELECT finds nothing, the contract fails 404. Neither failure is papered over as "provider unavailable, try later" — the error names the actual condition.
- `spa.standard` stays blocked after F2-01-A: `booking.resource.hold` still has no provider (no booking/resource implementation exists), and `inventory.stock.read` is optional so it never blocks. `booking.resource.hold` is a later slice, not smuggled into this one.

## 4. Guard endpoint (PROPOSED)

- The guard is wired at `POST /workspaces/{id}/rental/contracts` (`docs/06-ux-api.md:38`), together with that endpoint's business implementation in the following slice F2-01-B — not before, and not as a standalone helper. No guard implementation in F2-01-A.
- Guard order inside the contract transaction (after `requireDB`, `authedSubject`, `isValidUUID`): auth 401 → membership + write permission 403 → rental entitled 403 → rental active 403 with code `MODULE_NOT_ACTIVE` (`docs/06-ux-api.md:50` shows the shape) → referenced `customer_id` + `item_id` exist, are type-correct (`party.type='customer'`), and are readable in this workspace, else 404 → business conflict (e.g. duplicate contract reference) 409 → backend error 500 with the flat envelope and no SQL detail. Entitlement is re-checked at request time: revocation blocks future contracts and never grants them (R2 contract §6; B3 behavior).
- Core vs module-scoped, explicit: core endpoints (customers, catalog items) are always available to workspace members — they require auth + membership + permission + RLS, but no module installation. Module-scoped endpoints (rental contracts) additionally require the rental entitlement + active installation. "Always available" never means unguarded, and module checks are never silently applied to core reads.
- Open for F2-01-B (not decided here): the contract's price source — client-supplied agreed amount validated against `price_versions`, or server-side lookup of the effective price. Pricing stays out of F2-01-A either way.
